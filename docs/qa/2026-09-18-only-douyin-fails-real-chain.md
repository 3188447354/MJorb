| 时间 | 事件 |
|---|---|

两次都是 **112 秒**，中间**一行日志都没有**。

## 二、两次否定证据（先排除掉两个猜想）

### ① `退避` 零命中 ⇒ 退避重试一次都没触发

日志里搜「退避」**零命中**。所以 R24/R27/R29 加的退避重试**全部没被触发** ——
因为这两次失败的错误**不是** `isSessionExpiredError`（不是 1100，或描述里没有
"session has expired"）。

### ② 抖音两次**都没有** `App ID 名额` 那行 ⇒ 它根本没走到「建号」

`App ID 名额：…` 只在另外三次成功签名里出现。而抖音两次都没有
⇒ **失败发生在 Phase 1 的第一个请求 `fetchAppIDs`**（它排在名额诊断**之前**）。
**「扩展太多把 App ID 名额吃光」这个猜想，在这两次里是不成立的** —— 它连建号都没开始。

## 三、真正的差别：**要不要新建 App ID**

| 那次签名 | `App ID 名额` 说的 | 结果 |
|---|---|---|
| Seal 自续签（06:45） | 本次需 1 个…**需新注册 0 个** | ✅ 成功 |
| LiveContainer（06:47） | 本次需 4 个…**需新注册 0 个** | ✅ 成功 |
| 3105（06:53） | 本次需 1 个…**需新注册 0 个** | ✅ 成功 |
| **抖音（06:48 / 06:54）** | **（根本没写出来）** | ❌ 失败 |

**三次成功的签名，一次 App ID 都没新建。** 抖音要新建 **9 个**（主 App + 8 扩展）。

⇒ **差别不是证书、也不是扩展数量本身，而是「门户写入量」。**
账号被 Apple 限流之后，凡是「App ID 都已注册好」的 App 照样能签；
需要新建 9 个的抖音就撞在第一个请求上。

（该账号 `318***5***@qq.com` 当时只注册了 **1 个** App ID ⇒ 名额不是问题，
9 个新的完全放得下。所以这不是「7 天 10 个」用完了。）

## 四、用户踩的那个陷阱：App 自己把好文案覆盖掉了

06:56:32 那条「Apple ID 会话已过期 → 去「我的」重新验证」**不是真实原因**，是被改写过的：

`appIDFailure` 原本给出的文案是（代码注释里写明是特意写的）：

> Apple 暂时拒绝了请求 —— **本次签名的证书申请刚刚成功，说明登录状态其实还在**，
> 更常见的原因是短时间内请求过密被限流。**请先等几分钟再重试**；仍失败再重新验证、或改用其它 Apple ID。

但 `sign()` 里的一个 `catch` 会把**所有** `SEAL-AUTH-107` 无差别替换成：

> Apple ID 会话已过期 / 该 Apple ID 的登录状态已过期。签名过程中无法重新认证（网络环境不匹配），
> **请前往「我的」页面重新验证该 Apple ID 后再签名。**

⇒ 用户照做了（「重新添加 318***5***」），而**重新验证并不解决限流**
⇒ 越验证越糟 —— 这正是 `appIDFailure` 那段注释花力气要避免的死循环。

**这是「被动进入陷阱」的确切机制：不是用户不懂，是 App 让他去做了没用的事。**

## 五、三处修复

1. **`sign()` 的 catch 不再无差别替换**：保留原 `title` / `reason` / `recovery`
   （它们已按阶段区分且可执行），只**追加**一条「签名过程中 Seal 无法替你重新登录
   （此时网络要连着设备），需要重新验证请到「我的」页面」的环境说明。
2. **`fetchAppIDs` 过退避重试 + Phase 1 入口先留痕**：入口先写一条不依赖账号列表的
   `App ID 阶段开始：本次需 N 个 App ID（主 App 1 + 扩展 M），准备读取账号已有列表`，
   读列表本身也过 `withSessionRecovery("读取 App ID 列表")`。
3. **证书列表拉取失败要记原因与耗时**：原先 `try?` 把错误吞了，日志只有
   「Apple 证书列表暂不可用」，分不出是限流（1100）、超时还是网络。现在写
   `证书列表拉取失败：耗时 N 秒；疑似限流（1100）/非会话类错误；[domain code] description`。

**守卫**：R24 调用点计数 5→6；新增 R31（3 断言 + 3 变异）。**360 源码断言 + 196 变异 PASS。**

## 六、下次日志要看什么（判据）

1. **有没有 `App ID 阶段开始：本次需 9 个…`** —— 有它才说明这次真的走到了 Phase 1。
2. **有没有 `证书列表拉取失败：耗时 N 秒；…`** —— 它会直接告诉我们那 112 秒是什么：
   - `疑似限流（1100）` ⇒ 账号被 Apple 限流（等 / 换账号）；
   - `NSURLErrorDomain -1001`（超时）⇒ 网络/代理问题（换网络 / 挂对梯子）；
   - 其他 ⇒ 按 code 再判。
3. **失败时的日志码**：`SEAL-APPID-304` = App ID 名额满；`SEAL-AUTH-107` = 限流。
4. **有没有 `Apple 会话疑似被限流，退避 N 秒后重试 …`** —— 有它说明退避正在工作，耐心等。

## 七、给用户的操作建议（不依赖新构建）

1. **别再重新验证 Apple ID** —— 日志已证明登录是好的（同一账号 06:53 刚成功建证书并签名成功）。
2. **停手 15–30 分钟**：不签名、不重加账号、不进证书页。每次操作都在给限流续命。
3. **然后第一个就签抖音**（中间别插别的 App），让 9 个 App ID 一次建完。
4. 仍失败 ⇒ **换一个从没签过抖音的 Apple ID**（新账号没有限流历史，最有效）。
5. **不要删掉重装抖音** —— 卸载不解决限流，只会让你重跑一遍。

## 八、仍未解释的部分（诚实记录）

那 **112 秒**具体花在哪里，从这份日志**推不出来**：单个 Apple 请求的上限是 20/30 秒
（`withAppleTimeout`），所以 112 秒必然是**多次请求**；但链路上只有
`waitForCreatedCertificate`（最多 10 次 × 30 秒）是明确的多次循环，而第 2 次尝试
证书是「可复用」的、根本没走那里。**修复 3 就是为了让下一份日志直接给出答案。**
