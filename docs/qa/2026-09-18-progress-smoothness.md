# 进度条「跳着走」：进度不再是阶段枚举的纯函数

> 2026-09-18 · 用户反馈「百分比进度条和底部 5 个横杠都是跳着走的，不像 0→100 的丝滑，
> 后端处理时视觉上像卡住了」。本文记录根因、修复与验证状态。

## 一、现象与根因

用户原话：

> 目前签名续签安装流程的百分比进度条和底部的 5 个横杠的进度都是跳着走的，
> 而不是丝滑的从 0%–1%–2%–…–100%。后端处理时，会造成视觉上让人觉得是卡住了的感觉。

### 1.1 根因不是动效，是**信息**

进度是 `SigningStage` 的**纯函数**：10 个阶段 → 10 个写死的常数
（`SigningProgressView.overallProgress`：6/16/23/30/42/54/68/78→90/93/99），
**没有任何时间项**。所以两次阶段推送之间界面只能冻结，阶段一变就跳一格。
环上那句 `.animation(.easeInOut(duration: 0.45), value: progress)` 只是把跳变补间成
0.45 秒的滑动，本质仍是阶跃。

唯一有真实连续信号的只有 `.pushing`（AFC 上传回调），而它只占环的 **12%**（0.78→0.90）。

### 1.2 两个长阶段是观感杀手

| 阶段 | 真实耗时 | 旧实现显示 |
|---|---|---|
| `preparingBundle`（解压/改写/重签/打包） | 抖音 780 MB 实测 **112 秒** | 固定 **23%** |
| `.installing`（installd，不回进度） | 正常 7–11 秒，预算上限 2400 秒 | 固定 **93%** |

用户感知到的「卡住」，绝大部分就是这两段。而且第一段已经造成过实际伤害：
它原先的文案是「正在验证 Apple ID」，用户据此判断「Apple ID 验证卡住了」，
**于是去重新验证 Apple ID** —— 正是「重新验证 → 又被限流」死循环的入口
（见 `2026-09-18-only-douyin-fails-real-chain.md`）。

### 1.3 底部 5 横杠是另一处独立缺陷

`timelinePosition` 把 10 个阶段压成 5 格（1/3/2/1/3），而格内填充用的是**写死的常数**
（`segmentFraction`：0.33 / 0.5 / 0.67），与该格真实完成度**无关**。两个后果：

1. 当前格看起来像随机卡在某个位置；
2. 阶段一过，整条格子**一次变绿** —— 那是轨道上最大的一跳。

### 1.4 同一套语义写在**三处 switch** 里

`segmentFraction` / `overallProgress` / `timelinePosition` 各抄一遍同一套阶段语义
（本仓「同一条规则两份实现」已踩过 6 次以上）。所以这次改版的第一件事是**收敛成一张表**。

## 二、修复

### 2.1 新增 `SigningProgressBudget`（唯一数值来源）

`Seal/Core/Signing/SigningProgressBudget.swift`。每个阶段一对「地板 / 天花板」：

- `floor`：**进入本阶段时已确认到达**的进度（= 上一阶段的 `ceiling`）；
- `ceiling`：本阶段**估算的上界**（= 下一阶段的 `floor`）。

阶段内部指数收敛：

```
value(t) = floor + (ceiling − floor) · (1 − e^(−t / τ))
```

三个性质都是刻意的：

1. **永不越过天花板**（`1 − e^(−x) < 1`）⇒ 不会「提前到站」，阶段真正完成时数字也不回退；
2. **单调不减** ⇒ 阶段切换处 `ceiling_i == floor_{i+1}`，进度连续，不跳也不回退；
3. **先快后慢** ⇒ 越接近天花板爬得越慢，匹配「不知道还要多久」的直觉。

预算表（`τ` = 指数收敛时间常数）：

| 阶段 | floor → ceiling | τ | 真实信号 | 轨道格 / 格内序号 |
|---|---|---|---|---|
| `waitingForChannel` | 6 → 8 | 1.0 | — | 0 / 0（共 1） |
| `preparingAccount` | 8 → 14 | 1.6 | — | 1 / 0（共 3） |
| **`preparingBundle`** | **14 → 38** | **24** | — | 1 / 1 |
| `preparingCertificate` | 38 → 46 | 1.6 | — | 1 / 2 |
| `preparingAppID` | 46 → 58 | 3 | — | 2 / 0（共 2） |
| `preparingProfiles` | 58 → 66 | 3 | — | 2 / 1 |
| `signing` | 66 → 74 | 3 | — | 3 / 0（共 1） |
| `pushing` | 74 → 88 | 8 | **✅ 用真实值** | 4 / 0（共 3） |
| **`installing`** | **88 → 95** | **20** | — | 4 / 1 |
| `verifying` | 95 → 99.5 | 1.5 | — | 4 / 2 |

抖音 780 MB 的 `preparingBundle` 现在会爬到 **37.77%**（而不是钉在 23%）；
`.installing` 在 600 秒时停在 **94.9999999999993%** —— **永远不会声称装完**。

> ⚠️ 这套数值**不承诺**「完成百分比」，天花板以内是**估算**。所以界面必须把
> 「已确认」（`confirmedProgress`）与「估算」（`overallProgress`）画成**两种笔触**。
> 这也是 `InstallWaitNote` 当初「刻意不编造假百分比」那条判断的延续：
> 那里不编，是因为 `installing` 的耗时与包大小、设备 IO 都相关；
> 这里可以给估算，是因为**有上界**，不会出现「100% 了却还没装完」。

### 2.2 视觉：把「不确定」变成看得见的信号

1. **深色弧 = 已确认**（不随时间变化），**浅色弧 = 本阶段估算**（永远不会自己走到终点）。
   于是「浅色还在长」本身就是「还有活没干完」的信号，而深色弧顶上去了才是真的过了一个坎。
2. **扫光 + 呼吸点**：当前格有一条光带持续扫过，弧的前端有一个呼吸点。
   **它不推进百分比，只表达「在动」** —— 这是解决「后端干活时看着像卡住」的主力，
   比任何假百分比都可信（iOS 自己的不确定进度用的就是这个信号）。
   只在「估算中」的格子上画：有真实上传进度的格子本身就在动，再叠一层会像两个进度打架。
3. **轨道填充改为 `(格内已完成阶段数 + 本阶段完成比例) / 格内阶段总数`**，
   去掉写死的 0.33/0.5/0.67。因为 `ceiling_i == floor_{i+1}`，阶段完成时比例正好到 1、
   下一阶段从 0 起 ⇒ 衔接处不跳。
4. **长阶段的「本阶段已用时」**：超过 4 秒才显示（短暂阶段显示计时只会让人以为在拖时间）。
   `.installing` / `.verifying` 排除 —— 那两段由 `InstallWaitNote` 统一报等待，
   同一个数字在同一张卡片上出现两次会像故障。

### 2.3 驱动方式：逐帧，且**撤掉隐式动画**

`runningContent` 整体包进 `TimelineView(.animation(minimumInterval: 1.0/30.0))`，30Hz。
扫光、呼吸点、自替换转圈的相位全部由 `now` **直接算出**，不再用 `repeatForever` 动画 ——
卡片已经逐帧重绘，再挂一层隐式动画会互相打架（表现是黏滞 / 抖动 / 转速忽快忽慢）。
环上原有的 `.animation(.easeInOut(duration: 0.45), value: progress)` **必须撤掉**，同理。

### 2.4 阶段起点：规则也只许有一份

进度要按时间估算，就需要「进入当前阶段的时刻」。
新增 `SigningSession.stageStartedAt`，推进规则抽成
`InstallStageTimeline.stageStart(entering:currentStage:previous:now:)`
（与安装计时那条同属「起点簿记」，放在同一个类型里 —— 否则「起点该不该重置」
会有第二个地方各说各话）：

- 阶段变化 ⇒ 重置；
- 同一阶段被重复推送 ⇒ 保持（`.pushing` / `.installing` 都有哨兵 + 补发，每次重置会让估算永远停在起点）；
- 起点为 `nil` ⇒ 返回 `now`（返回 `nil` 等于这个阶段永远没有起点）。

同时把两个**绕过漏斗直接赋值 `status`** 的地方（`confirmCertificateSacrificeAndRetry`
的 `.preparingCertificate`、`restartSigning` 的 `.waitingForChannel`）改为统一走
`updateSigningStage` —— 否则那两个入口的进度会从**上一个阶段**的数值开始爬。

## 四、待真机验证

1. 抖音（780 MB）在「正在准备应用文件」阶段的百分比是否持续爬升、并显示「本阶段已用时」；
2. 安装阶段（`installing`）是否停在 95% 以下、扫光与呼吸点是否可见；
3. 底部轨道是否每次阶段推进都动一小格，而不是整条跳绿；
4. 阶段切换处数字是否**从不回退**（这是最容易在真机上看出问题的性质）。

## 五、已知取舍（用户已确认）

- 采用**混合**语义：有真实刻度的地方用真实值，其余用**有上界**的时间估算。
  「完全诚实」（只在 `.pushing` 给百分比）会让数字不丝滑；「全局插值到 100%」
  会在慢设备上出现「100% 了却还没装完」，反而更伤信任。
- 真实子事件（`prepare` 内部按 Mach-O 逐个回报、门户阶段按 bundle ID 回报）
  **本轮不做**，与「大包签名耗时归因埋点」合并成下一批 ——
  预算表的 `τ` 现在是估的，拿到真机分段耗时后要回头校准。
