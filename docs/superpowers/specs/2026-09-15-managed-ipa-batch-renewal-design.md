# Seal 1.0 普通 IPA 与一键续签设计

## 目标

让用户能够导入、签名、安装和续签普通 IPA，并通过一次主动操作续签本机所有由 Seal管理的已安装 App。普通 App全部处理完成后，Seal自身最后执行单 App自替换事务。

## 1.0 决策

- 一键续签由用户主动点击，不在后台自动发起。
- 一键续签包含所有本机已安装且由 Seal管理的 App，不按剩余天数筛选。
- 每个 App固定使用上次成功签名它的 Apple ID。
- 普通 App先执行，Seal最后执行。
- App自身失败不阻断其他 App。
- 配对、VPN和设备连接等全局故障暂停整批。
- 单个账号失效只暂停该账号分组，其他账号继续。
- 外部工具覆盖过的 App停止自动管理，用户确认接管后才能重新加入。
- 后台自动续签不进入1.0；是否进入后续版本单独评审。

## App 生命周期

普通 App使用以下状态：

1. `imported`：原始 IPA已经安全保存并完成解析。
2. `signed`：存在经过校验的签名产物，但尚未确认设备安装。
3. `installing`：安装请求正在执行。
4. `installedManaged`：设备确认存在，且Seal拥有续签所需来源和账号绑定。
5. `installedExternallyChanged`：设备仍有同 Bundle ID App，但可确认身份或版本已被外部改变。
6. `sourceMissing`：设备记录存在，但原始 IPA丢失或不可读。
7. `notInstalled`：Seal有记录或 IPA，但设备上没有该 App。
8. `stateUnknown`：设备通道不足以确认现实状态。

数据库状态不是最终事实。每次安装、续签和刷新列表时，用设备安装清单、设备描述文件及 Seal记录共同判断；读取失败显示“无法确认”，不能当成未安装或外部覆盖。

## 导入闭环

流程：

`选择或分享 IPA → 安全复制到 Seal存储 → 解析主 App与扩展 → 展示信息和限制 → 保存原始 IPA → 进入可签名状态`

要求：

- 拒绝路径穿越、损坏 ZIP、多个主 App、缺失 Info.plist或主可执行文件。
- 读取原始 Bundle ID、版本、最低系统版本、设备家族、扩展和权限。
- 原始 IPA与签名产物分开保存；重新签名永远从原始 IPA开始。
- 导入同一来源时先判断是替换原始包、保留新版本，还是另一个 App，不能静默覆盖。
- 不支持的权限在签名前明确说明会删除、降级或阻止签名。

导入不要求 Apple ID、配对或 VPN。用户可以先建立 App库，之后再完成环境。

## 单 App签名与安装

签名流程：

1. 确认原始 IPA仍存在且 SHA-256一致。
2. 选择该 App已绑定账号；首次签名由用户选择账号。
3. 检查账号会话和本机证书。
4. 固定 Bundle ID映射及全部扩展映射。
5. 获取描述文件并签名所有目标。
6. 回读候选 IPA，验证主程序、扩展、权限、Team、设备和证书。
7. 保存签名产物和候选身份，不推进已安装快照。
8. 设备通道就绪后提交安装。
9. 设备确认 App存在并匹配本轮目标后，才推进到期时间和已安装状态。

签名成功但安装失败时保留可复用签名产物，状态为 `signed`或保持原来的 `installedManaged`，不能把设备现实状态降成未安装。

## 一键续签候选集合

用户点击“一键续签”时生成不可变批次快照。纳入条件：

- 当前设备确认已安装。
- App由 Seal管理。
- 存在可读的原始 IPA。
- 存在明确的账号绑定。
- 没有被明确检测为外部覆盖。

Seal自身无论剩余时间多少都加入批次并永远排在最后。

以下对象不执行，但出现在预检结果中：

- 已从设备删除的 App。
- 原始 IPA缺失的 App。
- 账号已经删除或无法确认绑定的 App。
- 明确被外部工具覆盖、尚未重新接管的 App。
- 当前设备状态无法确认的 App。

## 多账号分组和顺序

普通 App按上次成功签名账号分组。分组顺序固定为：当前默认账号、其他账号按稳定标识排序。每组内按 App显示名称和固定 App ID排序，保证恢复后顺序一致。

执行规则：

1. 预检所有账号，不因为一个账号失效阻止有效账号开始。
2. 对有效账号组逐个处理普通 App。
3. 某个 App专属错误记录失败，继续同组下一个。
4. 某账号会话失效，暂停该账号剩余 App，继续其他账号组。
5. 所有普通 App处理完后执行 Seal。
6. Seal使用自己的绑定账号，不跟随当前默认账号。

## 故障分类

### App级故障：继续

- 原始 IPA损坏或丢失。
- App结构、扩展或权限不受支持。
- Bundle ID冲突只影响该 App。
- 单个 App签名或安装被 iOS明确拒绝。
- 单个 App候选验证不通过。

### 账号级故障：跳过该组

- Apple会话过期，且使用 Keychain密码自动重新登录失败或需要用户完成双重认证。
- 该 Team不可用。
- 该账号没有可用证书且无法安全释放槽位。

账号修复后从该账号第一个未完成任务继续，不重复续签本批已成功 App。

### 全局故障：暂停整批

- 配对文件失效或属于其他设备。
- LocalDevVPN/设备通道断开。
- 当前设备标识变化。
- 本地数据库、Keychain或事务队列无法可靠写入。

暂停前完成当前可安全落盘的状态；恢复环境后先核对可能已经提交的安装，再决定继续，不能盲目重传。

## Seal最后执行

普通 App队列完成或形成明确结果后，才进入 Seal任务。Seal使用已确认的自续签设计：单独的 SelfReplacementTransaction、一次安装提交、下次启动确认。

因为旧进程可能在覆盖安装时结束，批次摘要必须在提交 Seal之前写盘。新 Seal启动后完成自身对账，再把 Seal结果合并进原批次。

Seal失败不撤销普通 App的成功结果；最终批次显示“部分完成”。

## 批次持久化与恢复

`BatchRenewalTransaction`保存：批次 ID、创建时间、不可变候选列表、账号分组、每项状态、当前游标、全局暂停原因和 Seal自替换事务 ID。

每项状态为：等待、准备、签名、安装可能已提交、成功、失败、账号暂停、跳过、无法确认。

规则：

- 进入有外部副作用的步骤前先持久化。
- 安装超时或进程中断后标记“可能已提交”。
- 重启先核对设备事实，不直接重试。
- 用户可以取消尚未开始的项目；已经提交安装的项目只能等待核对。
- 新的一键续签不能覆盖未结算批次，必须先继续或结束旧批次。

## 外部覆盖处理

只有获得正面证据时才标记外部覆盖，例如设备报告的版本、Team、描述文件或映射 Bundle身份与上次成功安装快照明确不一致。

检测后：

- 停止该 App自动管理和一键续签。
- 保留原始 IPA、历史和旧账号绑定。
- 不自动覆盖设备上的外部版本。
- 显示变化证据。
- 用户重新导入对应 IPA，或在确认页面选择“由 Seal重新接管”后，才允许重新签名覆盖。

无法读取足够证据时显示 `stateUnknown`，不能误报外部覆盖。

## 结果页

结果按三组展示：成功、需要处理、未执行。每项显示 App、使用账号、完成阶段和下一步。

批次顶部只出现以下结论之一：

- 全部完成。
- 部分完成。
- 已暂停，可继续。
- 等待重新打开 Seal确认。
- 需要电脑恢复 Seal。

用户修复账号或通道后点击“继续未完成项目”，不重新创建全量批次。

## 验收标准

1. 点击一次会纳入所有本机已安装且由 Seal管理的 App，不按到期时间筛选。
2. 所有普通 App在 Seal之前执行。
3. App A失败后 App B仍能成功。
4. 一个账号过期只暂停该账号组，其他账号继续。
5. VPN或配对失败暂停全批，恢复后不重复已成功项目。
6. 原始 IPA缺失时明确要求重新导入，不尝试从签名产物反推原包。
7. 签名成功但安装失败不伪造新的设备到期时间。
8. 外部覆盖只有在证据明确时成立，并停止自动管理。
9. Seal提交安装前批次状态已经落盘；新进程能补上 Seal结果。
10. 整批中同一个安装任务不会因超时或重启自动重复提交。
