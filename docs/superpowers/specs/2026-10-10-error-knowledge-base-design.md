# Seal 错误知识库设计

## 目标

让 Seal 的错误弹窗、日志导出、应用内解决办法和官网帮助中心引用同一份可审计知识，避免把临时环境问题或不完整线索误说成确定根因。

## 已知现状

- `ImportFailure` 只有 `title`、`reason`、`recovery` 与 `code` 四个字段；错误码和用户文案分散在 Swift 源码中。
- 当前源码有 396 个唯一 `SEAL-*` 码。`docs/qa/log-code-index.md` 只记录已在真机日志中出现过的部分，且通过手工表格维护。
- App 的错误弹窗已经可跳转至 `https://ios.sealsign.eu.cc/help/?q=<code>`；官网帮助中心已经支持按错误码检索。
- `Scripts/verify-release-safety.py` 已对“索引中出现的码仍在源码中”做静态检查，但不能保证全部可见错误都有准确的归因、恢复操作与帮助文档。

## 范围与非目标

第一期覆盖所有用户可见 `ImportFailure` 码，以及会进入日志详情、但不一定是失败的关键诊断码。它优先审计登录、证书、描述文件续签、安装/设备通道、存储、导入与自更新链路。

第一期不做以下事情：

- 不将日志信息级事件标成错误。
- 不把没有底层返回值或状态证据的情况写成确定根因。
- 不在没有官网源代码或发布权限的前提下直接改线上帮助页面。
- 不改变签名、安装或续签业务决策，只收敛诊断、展示与回归约束；发现错误归因后按独立缺陷修复。

## 单一数据源

新增仓库内版本化目录 `docs/error-catalog/`。每个条目使用机器可读 JSON，字段为：

- `code`：唯一 `SEAL-*` 码。
- `kind`：`failure`、`warning` 或 `diagnostic`。
- `confidence`：`confirmed`、`conditional` 或 `unknown`。
- `evidence`：能让该结论成立的返回值、设备状态或日志前提。
- `summary`：面向用户的一句话解释。
- `notEvidenceOf`：明确不应从该码推断出的结论。
- `actions`：按顺序给出的恢复步骤；每项有可显示文本和可选 App 内路由。
- `supportData`：仍未解决时所需的日志片段与脱敏信息。
- `source`：Swift 文件与符号，供审计者追溯。

目录附带 `schema.json`，并按模块拆分文件，防止一个数百项大文件同时成为冲突热点。目录的聚合索引与官网导出物由脚本生成，不由人手维护。

## 证据等级

| 等级 | 含义 | App 文案规则 |
|---|---|---|
| `confirmed` | 底层返回、持久化状态或操作后读回明确支持该结论 | 可以使用“已确认”。 |
| `conditional` | 码只描述现象，存在多种可能根因 | 用“可能”并列出判断条件；恢复步骤先做无损检查。 |
| `unknown` | 原始错误无法安全分类 | 不猜原因；展示原始脱敏诊断和导出日志入口。 |

任何从底层错误映射到 `confirmed` 的条目都必须记录可验证的证据。缺少证据时，CI 拒绝将其标为 `confirmed`。

## 应用内行为

保留现有主恢复按钮。错误弹窗的“查看解决办法”优先打开应用内“错误说明”页；页面离线展示目录内容、证据等级、可执行步骤与“复制诊断”。网页作为“更多帮助”入口，保留错误码查询参数。

日志页选择某条错误时，使用相同目录显示解决办法；只有目录未覆盖的码才显示“尚未能确认原因”，并提供导出日志。日志事件的 `warning`/`diagnostic` 视觉上明确标注，不与终态失败混淆。

## 官网同步

生成脚本从 `docs/error-catalog/` 产出稳定 JSON：`docs/error-catalog/generated/help-index.json`。发布工作流只同步版本更新；帮助中心的内容同步必须由独立、可重试、可验证的步骤执行。

在获得官网源仓库/部署入口后，官网读取该 JSON 或由同一脚本生成静态帮助条目。上线前比较 App 导出物与官网响应，确保码、标题、证据等级和恢复步骤一致。

## CI 约束

新增验证脚本，至少保证：

1. 所有 catalog 码在源码中唯一存在；不存在的码必须移入历史表并标注移除版本。
2. 所有已登记的用户可见 `ImportFailure` 码都有目录项。
3. `confirmed` 条目包含非空证据；`conditional` 与 `unknown` 条目包含 `notEvidenceOf`。
4. 动作文案不可为空；引用的 App 路由必须存在。
5. 生成物可复现，生成后工作区无差异。

## 审计与修复流程

每个模块按“错误产生点 -> 包装/转换 -> 日志 -> UI -> 恢复动作”追踪。审计结论只能分为：

- 归因正确：登记证据与恢复步骤；
- 归因过强：降为 `conditional` 或 `unknown`；
- 映射错误：先写回归测试，再在产生/转换处修复；
- 证据不足：增加脱敏诊断字段与日志，不改业务结果。

每一个真实 bug 修复必须追加 `DEBUG_LOG.md`，并带最小回归测试；使用完整 iOS CI 验证。

## 验收

1. 用户可在离线 App 内按错误码看到准确等级与解决办法。
2. 对同一错误码，日志页、错误弹窗与官网导出的文字一致。
3. 无法确认根因时，界面不会写“ID 失效”“需要重签名”等确定性措辞。
4. 新增/删除用户可见错误码会使 CI 在目录未更新时失败。
5. 高风险模块的每个现有用户可见错误码都经过一次证据审计并留下来源。
