# Seal 源码错误标识审计设计

## 目的

建立唯一、可再生成、可追溯的错误标识审计清单。它回答“一个标识在哪里产生、是不是用户可见失败、已由什么源码证据确认、用户下一步能做什么”，而不是仅按字符串前缀或旧帮助文案猜测。

## 已确认的基线

2026-10-11 对 `Seal/**/*.swift` 的原始字面量扫描得到 424 个不同 `SEAL-*` 标识、797 处出现。这个数字是源码标识总量，不是用户错误数：它包含注释、操作日志、后台事件和失败构造候选。

其中 136 个不同标识（144 次出现）处于直接 `ImportFailure` 构造边界；43 次已显式携带结构化合同字段，101 次仍只依赖默认语义。这 101 次是后续迁移清单，不得被视为已完成分类。来源角色会重叠：同一个编号可同时被产生、路由和记录日志，因此各角色计数不可相加为总数。

旧正则只接受两段加数字尾号，漏掉了 `SEAL-UPDATE-DL-501`、`SEAL-IPA-ROLLBACK-001` 等多段标识；也会把 `SEAL-OP` 这类日志标签误报为错误码。因此旧“389 条未分类错误”的说法无效。

## 标识与来源分类

每次出现同时记录两种互不混淆的分类。

### 标识类型

| 类型 | 含义 | 是否计入稳定错误码 |
| --- | --- | --- |
| `standard_error_code` | 以数字段结尾的稳定标识，例如 `SEAL-INSTALL-710`、`SEAL-UPDATE-DL-501` | 是 |
| `legacy_error_identifier` | 确实从失败边界发出，但不符合数字尾号规范，例如 `SEAL-APPID-DEVICELIMIT` | 是，且必须列入迁移清单 |
| `diagnostic_tag` | 操作日志、轮次总结或调试标签，例如 `SEAL-OP`、`SEAL-RENEW-ROUND` | 否 |

`legacy_error_identifier` 不会被静默改名：先建立旧值到新值的兼容映射、补回归测试，再迁移调用点与历史日志读取。

### 来源角色

| 角色 | 含义 | 可否直接写用户文案 |
| --- | --- | --- |
| `failure_emission_candidate` | 失败对象或错误转换点的候选发出位置 | 不可；仍须完成完整链路审计 |
| `internal_event_or_log` | 运行日志、后台事件、操作总结或下载诊断 | 不可 |
| `comment_reference` | 注释、设计说明或历史引用 | 不可 |
| `executable_reference` | 比较、路由、策略表或其他可执行引用 | 不可；可能是消费点而非产生点 |

### 自动证据状态与人工审计结论

生成器的 `auditStatus` 只描述**当前源码证据是否完整**，不等同于用户帮助页的最终结论：

| 自动状态 | 含义 |
| --- | --- |
| `contracted` | 该标识的所有直接失败构造均写明结构化字段 |
| `mixed` | 同一标识同时存在合同化和旧构造出口 |
| `unreviewed` | 存在直接失败构造，但至少一个出口没有结构化字段 |
| `conflicted` | 同一稳定码在直接出口中写入互相冲突的具体条件或动作，必须拆码或统一语义 |
| `diagnostic_only` | 只用作内部诊断标签 |
| `reference_only` | 没有直接失败构造，只存在注释、路由或其他引用 |

人工审计完成后，才在审计记录中给出 `audited_user_failure`、`audited_user_warning` 等业务结论。自动状态绝不推导用户操作，也不能替代逐条触发链核验。

## 审计合同

每个稳定或遗留错误标识先以 `unreviewed` 入册。只有完成下列证据链，才允许提升状态：

```
实际触发条件
  -> 产生或转换错误的函数
  -> 上层是否重写、重试或降级
  -> UI / 日志出口
  -> 已验证的唯一恢复动作
```

最终状态只能是：

- `audited_user_failure`：确定进入用户失败 UI，并有可执行恢复动作；
- `audited_user_warning`：用户需要知晓，但不代表本次操作失败；
- `audited_internal_diagnostic`：仅保留诊断与日志；
- `audited_reference_only`：没有运行时发出点；
- `superseded`：已被兼容映射替代，保留历史读取。

任何没有完整证据链的条目保持 `unreviewed`。不得把“检查 Wi-Fi”“开启 LocalDevVPN”“重新签名”写成默认答案；动作必须由对应条件能被该操作改变的源码证据支持。

直接 `ImportFailure` 构造必须显式填写至少一个结构化合同字段；优先完整填写 `condition`、`action`、`retryDisposition`、`operation` 与 `origin`，只有确有界面内入口时填写 `route`。在迁移完成前，生成清单记录无结构化字段的基线数量，禁止新增。

## 工具与 CI 规则

`Scripts/error_code_inventory.py` 扫描生产 Swift，输出每个标识的精确路径、行号、来源角色、标识类型和审计状态。生成文件为 `docs/qa/generated/error-code-inventory.json`，不是 App 内静态帮助页，也不参与用户界面。

测试必须覆盖：多段标识不会截断、注释不会升格为失败、日志 `code:` 字段不会升格为失败、非数字遗留失败标识会被显式标记。后续 CI 守卫必须拒绝新增未入册的失败发出点，并拒绝把 `unreviewed` 条目作为用户操作依据。

## 审计顺序

1. Apple 登录与开发者门户：`AUTH`、`ANI`、`NET`；
2. 签名身份、证书、App ID、描述文件：`CERT`、`APPID`、`PROFILE`、`SIGN`；
3. LocalDevVPN、配对、安装结果：`PAIR`、`VPN`、`INSTALL`；
4. 单续签、全部续签、自替换：`RENEW`、`SELF`；
5. 导入、存储、日志与维护：`IPA`、`STORAGE`、`LOG`。

每一阶段先审产生边界和跨入口重写点，再修改用户文案或恢复按钮。没有完成前，不宣称“全部错误已经分类”。
