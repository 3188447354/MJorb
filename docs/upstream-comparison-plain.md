# Seal ↔ 上游 全链路对比（大白话版）

- 生成：2026-09-19
- **上游** = SideStore（主参考）+ AltStore（它的父项目）+ AltSign（发请求的库）+ AnisetteKit（造设备身份的库）+ rork-sign（签名内核）
- **数据来源**：`docs/upstream-alignment.md`（8 条对照台账）+ 本轮实测 ✓
- **「谁更好」这一列是结论**，不是中立描述 ✓ —— 但每条都写了**为什么** ✓

---

## 一句话总览

> **两边的「主干」一样**（都是：取设备身份 → 拿证书 → 建 App ID → 取描述文件 → 重签 → 装机），
> **差别全在细节**：
> - **Seal 多了**：自动重试、诊断日志、守卫、对失败的分级处理；
> - **Seal 少了**：并发、蜂窝批量、图形界面的一些打磨；
> - **Seal 错过的**：**上游「每次请求前换一份新设备身份」的用法** ✗（今天最大的 bug 就是这个 ✓）。

---

## 二、逐环节对比

| 环节 | **Seal（我们）** | **上游（SideStore / AltStore）** | 谁更好 |
|---|---|---|---|
| **1. 设备身份（anisette）**<br>*Apple 用来认「这台设备」的凭证，含一次性码* | 取一次，塞进会话，**用一整轮** ✗ | **每次要发请求前，重新取一份** ✓ | **上游对** ✓<br>已按上游修好（`921fa4e` / `83084d0`）<br>⚠️ 这是今天 1100 报错的**根因** |
| **2. 证书——先建还是先撤** | **先撤销旧的，再建新的** ✗ | **先建；建不成才撤销** ✓ | **上游对** ✓<br>已按上游改（`ff718d9`）<br>※ 免费账号只有 1 张证书，两边实际差别只在付费账号 ✓ |
| **3. 证书——谁决定撤哪张** | 程序**自动**决定 ✓（用户不用管） | **弹窗让用户勾选** ✓ | **Seal 更省事** ✓<br>但上游更安全（人兜底 ✓）<br>**按你的决定：保留自动撤销** ✓ |
| **4. 证书——什么算「能用」** | 本机有私钥 **且** 剩余寿命 **> 7 天** ✓ | 在 Apple 门户列表里就算能用（不在才查 OCSP）✓ | **Seal 对** ✓<br>上游那样会把「明天就过期」的证书签进去 ⇒ **装完闪退** ✗<br>※ 这条**不能**当「多余的严格」去掉 |
| **5. App ID——先建哪个** | **主 App 排最前** ✓ | **也是主 App 先** ✓ | **一样** ✓ |
| **6. App ID / 描述文件——串行还是并发** | **一个一个来**，每个请求间隔 0.4 秒 ✗ | **同时开多个**（并发），不限速 ✓ | **待定** ⏸<br>Seal 的限速是为「1100」加的，但那可能是**误诊**（真因是第 1 条）<br>⇒ **先测一次**：不再 1100 就去掉限速 ✓ |
| **7. 描述文件——怎么进设备** | 跟着 IPA 一起装 ✓ | 也是跟着装；**蜂窝网络下会攒一批一起装** ✓ | **各有场景** ✓<br>Seal 没有「蜂窝」这个概念 ⇒ 不用跟 ✓ |
| **8. 重签（签名内核）** | rork-sign **+ 4 个补丁** ✓ | rork-sign 原版 ✗ | **Seal 多** ✓<br>其中一条修的是**装完启动就崩**（FairPlay 标记）✗<br>⚠️ 补丁以前**没记录**，同步上游会**静默丢失** ⇒ 已加守卫 R52 ✓ |
| **9. 重签——大文件处理** | 用**内存映射**（不把整个文件读进内存）✓ | 直接整块读 ✗ | **Seal 多** ✓<br>今天刚加（`6c8755f` / `4009d75` / `658a25e`）<br>※ 针对「签抖音崩在最大框架」 |
| **10. 会话过期（1100）怎么办** | **自动退避重试 + 重建会话** ✓ | **完全不处理** ✗（用户自己重试） | **Seal 多** ✓<br>上游连代码都没有 ⇒ 这是**必要的健壮性**，保留 ✓ |
| **11. 装完之后** | 会**回收旧描述文件**、**核验证书归属**、**自替换结算** ✓ | 基本不做 ✓ | **Seal 多** ✓ |
| **12. 出问题怎么查** | **阶段日志 + 时间分片 + 逐文件诊断 + 33 个日志码** ✓ | 少量 debug 日志 ✗ | **Seal 多** ✓ |
| **13. 免费账号限制** | 有**设备级 3 个 App 上限**的判定 ✓ | 没有 ✗ | **Seal 多** ✓ |
| **14. 界面 / 交互** | 自己的 ✓ | 更成熟（多年打磨 ✓） | **上游更成熟** ✗ |
| **15. 代码组织** | 自己的命名与结构（`Seal/…`）✗ | `ALT*` / AltStore 风格 ✓ | **无法逐行对照** ✗<br>同名文件只有 1 个、相似度 0.004–0.121 |

## 三、结论（三句话）

1. **主干流程两边一样** ✓ —— 所以上游的**做法**值得跟（今天已跟了 2 条 ✓）；
2. **Seal 多出来的东西分两类** ✗✓：
   - **「更严格」**（白撤证书 / 过度限速）⇒ **该去掉** ✓
   - **「更完整」**（自动重试 / 诊断 / 守卫）⇒ **该保留** ✓
3. **唯一能逐字对照的地方是签名内核**（`Vendor/rork-sign` = 上游 0.6.5 + 4 个文件的补丁 ✓）——
   精确 diff 在 `docs/upstream/rork-sign-0.6.5-vs-Vendor.diff` ✓
